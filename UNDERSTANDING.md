## System Overview

The Inventory Management System is a sophisticated, event-driven application designed to automate inventory tracking, reordering, and warehouse capacity management. It operates on a **microservices-inspired architecture** with clear separation of concerns.

### Key Components:
- **Frontend**: React-based dashboard for real-time inventory visualization
- **Backend API**: Fastify-powered REST API with WebSocket support
- **Database**: PostgreSQL with Prisma ORM
- **Cache**: Redis for performance optimization
- **Message Queue**: RabbitMQ for async job processing
- **Scheduler**: Cron-based jobs for periodic tasks

## Core Flows - Happy Paths

### 1. Product Creation Flow

**Trigger**: User creates a new product via API or frontend

**Steps**:
```
1. API Request → POST /api/products
   ↓
2. Controller Validation (Joi schema)
   - sku: required, unique string
   - name: required string
   - reorderThreshold: minimum stock level
   - reorderQuantity: default order quantity
   - defaultSupplierId: UUID reference to supplier
   ↓
3. Service Layer (product.service.ts)
   - prisma.product.create() with supplier relation
   ↓
4. Database Insert
   - Creates product record
   - Links to defaultSupplier
   ↓
5. Response
   - Returns created product with supplier details
   - Status 201 Created
```

**Happy Path Result**: Product is created and ready for stock management

---

### 2. Stock Monitoring & Automatic Reordering Flow

**Trigger**: Scheduled cron job runs every N minutes (configurable via `STOCK_CHECK_INTERVAL_MINUTES`)

**Steps**:
```
1. Scheduler Trigger (jobs/scheduler.ts)
   - Cron job executes stockMonitor.checkStockLevels()
   ↓
2. Find Low Stock Products (stockMonitor.service.ts)
   - Query: prisma.productStock.findMany()
   - Filter: quantity <= product.reorderThreshold
   - Include: product, warehouse relations
   - Exclude: products with pending orders (status: PENDING | IN_TRANSIT)
   ↓
3. For Each Low Stock Product:
   a. Check Warehouse Capacity
      - Calculate: availableSpace = capacity - currentStock - pendingOrders
      - Determine: optimal order quantity

   b. Calculate Order Quantity
      - Start with: product.reorderQuantity
      - Adjust for: warehouse capacity
      - Result: min(reorderQuantity, availableSpace)

   c. Create Purchase Order
      - Generate unique orderNumber: PO-YYYYMMDD-TIMESTAMP
      - Calculate: totalCost = unitPrice × quantity
      - Set: expectedArrivalDate = orderDate + leadTimeDays
      - Mark: isAutoGenerated = true
   ↓
4. Publish to Queue (RabbitMQ)
   - Queue: order.process.queue
   - Message: { productId, warehouseId, supplierId, quantity }
   - Priority: 5 (medium)
   ↓
5. Alert Creation
   - Type: LOW_STOCK
   - Severity: WARNING
   - Message: "Product {name} in {warehouse} below threshold"
   ↓
6. Consumer Processing (jobs/queueWorkers.ts)
   - Receives message from queue
   - Executes: stockMonitor.createPurchaseOrder()
   - With retry logic (max 3 attempts)
   ↓
7. Order Confirmation
   - Order status: PENDING
   - Logged in database
   - Alert generated
```

**Happy Path Result**:
- Low stock products identified
- Purchase orders automatically created
- Alerts generated for monitoring
- Orders tracked in database

### 3. Purchase Order Arrival Flow

**Trigger**: User marks order as "ARRIVED" via API

**Steps**:
```
1. API Request → POST /api/purchase-orders/{id}/arrive
   ↓
2. Service Layer (purchaseOrder.service.ts)
   - Publishes to queue: order.arrival
   - Priority: 8 (high)
   - Returns: "Order arrival is being processed"
   ↓
3. Queue Consumer (jobs/queueWorkers.ts)
   - Receives arrival message
   - Processes: handleOrderArrival()
   ↓
4. Transaction Processing (Prisma $transaction)

   a. Update Purchase Order
      - status: 'ARRIVED'
      - actualArrivalDate: new Date()

   b. Update/Create ProductStock
      - Find existing: productStock.findUnique()
      - If exists: increment quantity
      - If not: create new record

   c. Update Warehouse Current Stock
      - warehouse.currentStock += quantityOrdered

   d. Create Stock Movement Record
      - type: PURCHASE_ORDER_ARRIVAL
      - quantity: quantityOrdered (positive)
      - reference: orderNumber
      - performedBy: 'SYSTEM'

   e. Invalidate Cache
      - Delete: product cache
      - Delete: warehouse cache
      - Delete: warehouse capacity cache
   ↓
5. Capacity Check
   - Calculate new utilization
   - If > 90%: Create CAPACITY_WARNING alert
   - If > 100%: Create CAPACITY_EXCEEDED alert (critical)
   ↓
6. Response
   - Order status updated
   - Stock levels updated
   - Audit trail created
```

**Happy Path Result**:
- Order marked as arrived
- Stock quantities updated atomically
- Warehouse capacity tracked
- Full audit trail maintained
- Alerts generated if needed

### 4. Manual Stock Adjustment Flow

**Trigger**: User manually adjusts stock (damage, returns, corrections)

**Steps**:
```
1. API Request → POST /api/products/adjust-stock
   Body: {
     productId: UUID,
     warehouseId: UUID,
     quantityChange: number (positive or negative),
     reason: string,
     performedBy: string
   }
   ↓
2. Validation (Joi)
   - All fields required
   - quantityChange: can be positive or negative
   ↓
3. Service Layer (stockMonitor.service.ts)
   - stockMonitor.adjustStock()
   ↓
4. Find Current Stock
   - Query: productStock.findUnique({ productId, warehouseId })
   - If not exists: create new record with quantity = 0
   ↓
5. Validation Checks
   - If quantityChange < 0 (reduction):
     → Check: currentQuantity + quantityChange >= 0
     → Reject if would result in negative stock
   ↓
6. Transaction Processing

   a. Update ProductStock
      - New quantity: currentQuantity + quantityChange
      - Update lastUpdated

   b. Update Warehouse
      - If increase: warehouse.currentStock += quantityChange
      - If decrease: warehouse.currentStock -= abs(quantityChange)

   c. Create StockMovement
      - type: MANUAL_ADJUSTMENT
      - quantity: quantityChange
      - reason: user-provided reason
      - performedBy: user identifier

   d. Invalidate Caches
   ↓
7. Response
   - Success message
   - Updated stock levels returned
```

**Happy Path Result**:
- Stock adjusted according to user input
- Warehouse totals updated
- Complete audit trail with reason
- Caches invalidated for consistency

### 5. Warehouse Capacity Management Flow

**Trigger**: Any operation that changes warehouse stock

**Steps**:
```
1. Capacity Check Request
   - Called before creating purchase orders
   - Called during order arrival
   ↓
2. Get Warehouse Data (with caching)
   - Check Redis cache first
   - If miss: Query database
   - Cache for 5 minutes (CACHE_TTL.WAREHOUSE)
   ↓
3. Calculate Pending Orders
   - Query: purchaseOrder.aggregate()
   - Filter: warehouseId + status IN (PENDING, IN_TRANSIT)
   - Sum: quantityOrdered
   ↓
4. Calculate Projected Stock
   projectedStock = currentStock + pendingOrdersTotal
   ↓
5. Determine Available Space
   availableSpace = capacity - projectedStock
   ↓
6. Capacity Analysis
   - hasCapacity: availableSpace >= requestedQuantity
   - utilizationPercentage: (projectedStock / capacity) × 100
   - recommendedQuantity: min(requestedQuantity, availableSpace)
   ↓
7. Return CapacityCheck Object
   {
     hasCapacity: boolean,
     availableSpace: number,
     currentStock: number,
     maxCapacity: number,
     utilizationPercentage: number,
     recommendedQuantity?: number
   }
   ↓
8. Decision Logic
   - If hasCapacity: proceed with order
   - If !hasCapacity && availableSpace > 0: adjust order quantity
   - If availableSpace <= 0: reject order
   ↓
9. Alert Generation (if needed)
   - 90-99% utilization: CAPACITY_WARNING
   - ≥100% utilization: CAPACITY_EXCEEDED (CRITICAL)
```

**Happy Path Result**:
- Orders never exceed warehouse capacity
- Automatic adjustment of order quantities
- Proactive alerts for capacity issues
- Efficient caching for high performance

### 6. Product Deletion (Soft Delete) Flow

**Trigger**: User attempts to delete a product

**Steps**:
```
1. API Request → DELETE /api/products/{id}
   ↓
2. Pre-deletion Validation

   a. Check Pending Orders
      - Query: purchaseOrder.count()
      - Filter: productId + status IN (PENDING, IN_TRANSIT)
      - If count > 0: REJECT with error

   b. Check Active Stock (implied)
      - Products with stock can still be deleted
      - Stock records remain for audit trail
   ↓
3. Soft Delete
   - Update: product.isActive = false
   - Does NOT delete database record
   - Product hidden from active queries
   ↓
4. Cache Invalidation
   - Delete: CACHE_KEYS.PRODUCT(id)
   ↓
5. Response
   - Success message
   - Product marked inactive
```

**Happy Path Result**:
- Product hidden from system
- Historical data preserved
- Prevents deletion with active orders
- Audit trail maintained

## Edge Cases & Error Handling

### 1. Concurrent Order Creation (Race Condition)

**Problem**: Multiple schedulers/processes create duplicate orders for same product

**Detection**:
```javascript
// Check for existing pending order
const existingOrder = await prisma.purchaseOrder.findFirst({
  where: {
    productId,
    warehouseId,
    status: { in: ['PENDING', 'IN_TRANSIT'] }
  }
});
```

**Prevention**:
1. **Idempotency Check**: Always check for existing orders before creation
2. **Database Constraint**: Unique index on `orderNumber`
3. **Retry Logic**: On constraint violation (P2002), generate new order number
4. **Exponential Backoff**: 100ms delay between retries

**Resolution**:
```javascript
let retries = 3;
while (retries > 0) {
  try {
    const orderNumber = await generateOrderNumber(); // Timestamp-based
    await prisma.purchaseOrder.create({ data: { orderNumber, ... }});
    break; // Success
  } catch (error) {
    if (error.code === 'P2002' && retries > 1) {
      retries--;
      await sleep(100);
    } else {
      throw error;
    }
  }
}
```

### 2. Warehouse Over-Capacity

**Problem**: Order would exceed warehouse capacity

**Detection**:
```javascript
const capacityCheck = await capacityManager.checkWarehouseCapacity(
  warehouseId,
  requestedQuantity
);

if (!capacityCheck.hasCapacity) {
  // Handle over-capacity scenario
}
```

**Handling Strategies**:

**Strategy 1: Automatic Adjustment**
```javascript
if (capacityCheck.availableSpace > 0) {
  // Reduce order to fit available space
  const adjustedQuantity = capacityCheck.recommendedQuantity;
  logger.warn('Order quantity adjusted due to capacity');
}
```

**Strategy 2: Split Order**
```javascript
// Find alternative warehouse with capacity
const alternativeWarehouses = await findWarehousesWithCapacity(
  requiredQuantity - availableSpace
);
// Create multiple orders if feasible
```

**Strategy 3: Rejection**
```javascript
if (capacityCheck.availableSpace <= 0) {
  throw new Error('Warehouse at full capacity');
}
```

**Alert Creation**:
- **90% utilization**: WARNING alert (plan ahead)
- **100% utilization**: CRITICAL alert (immediate action needed)

---

### 3. Negative Stock Prevention

**Problem**: Manual adjustment would result in negative stock

**Validation**:
```javascript
const currentStock = await prisma.productStock.findUnique({
  where: { productId_warehouseId }
});

const newQuantity = currentStock.quantity + quantityChange;

if (newQuantity < 0) {
  throw new Error(
    `Cannot reduce stock by ${Math.abs(quantityChange)}. ` +
    `Current stock: ${currentStock.quantity}`
  );
}
```

**Prevention**:
- Pre-flight validation before database update
- Transaction rollback on constraint violation
- User-friendly error messages with current stock info

### 5. Order Cancellation After Arrival

**Problem**: User attempts to cancel already-arrived order

**Validation**:
```javascript
const order = await prisma.purchaseOrder.findUnique({

if (order.status === 'ARRIVED') {
```

**Allowed States for Cancellation**:

- CANCELLED → CANCELLED ❌

**Side Effects of Cancellation**:

### 6. Queue Processing Failures

**Problem**: Message processing fails in queue consumer

**Error Handling Strategy**:

**Retry Mechanism**:
```javascript
channel.consume(queue, async (msg) => {
  try {
    const content = JSON.parse(msg.content.toString());
    await handler(content);
    channel.ack(msg); // Success
  } catch (error) {
    logger.error(`Error processing message: ${error}`);
    channel.nack(msg, false, false); // Reject, don't requeue
    // Message goes to dead-letter queue if configured
  }
});
```

**Dead Letter Queue (DLQ)**:
- Failed messages moved to DLQ
- Manual inspection and retry possible
- Prevents infinite retry loops

**Monitoring**:
- Log all failures with context
- Alert on high failure rates
- Dashboard for DLQ monitoring

### 7. Cache Invalidation Issues

**Problem**: Stale cache data causes inconsistencies

**Cache Invalidation Strategy**:

**Write-Through Pattern**:
```javascript
async updateProduct(id, data) {
  // 1. Update database
  const product = await prisma.product.update({ where: { id }, data });

  // 2. Invalidate cache immediately
  await CacheService.del(CACHE_KEYS.PRODUCT(id));

  // 3. Return updated data
  return product;
}
```

**Multi-Key Invalidation**:
```javascript
async updateWarehouse(id, data) {
  await prisma.warehouse.update({ where: { id }, data });

  // Invalidate all related caches
  await Promise.all([
    CacheService.del(CACHE_KEYS.WAREHOUSE(id)),
    CacheService.del(CACHE_KEYS.WAREHOUSE_CAPACITY(id))
  ]);
}
```

**TTL Strategy**:
- Short TTL for frequently changing data (5 minutes)
- Longer TTL for stable data (1 hour)
- Critical data: always check DB after cache

### 8. Database Transaction Failures

**Problem**: Partial updates during multi-step operations

**Atomic Operations with Prisma Transactions**:

```javascript
await prisma.$transaction(async (tx) => {
  // All operations succeed or all rollback

  // 1. Update order
  await tx.purchaseOrder.update({
    where: { id },
    data: { status: 'ARRIVED' }
  });

  // 2. Update stock
  await tx.productStock.upsert({
    where: { productId_warehouseId },
    update: { quantity: { increment: quantityOrdered }},
    create: { productId, warehouseId, quantity: quantityOrdered }
  });

  // 3. Update warehouse
  await tx.warehouse.update({
    where: { id: warehouseId },
    data: { currentStock: { increment: quantityOrdered }}
  });

  // 4. Create audit record
  await tx.stockMovement.create({
    data: { type: 'PURCHASE_ORDER_ARRIVAL', ... }
  });
});
```

**Benefits**:
- All-or-nothing guarantee
- Automatic rollback on error
- Consistent state maintenance

### 9. Order Number Collision

**Problem**: Two orders generate same order number

**Original Issue** (Counter-based):
```javascript
// ❌ RACE CONDITION
const count = await prisma.purchaseOrder.count({ ... });
const orderNumber = `PO-${year}${month}-${count + 1}`;
// Two requests could get same count!
```

**Solution** (Timestamp-based):
```javascript
// ✅ UNIQUE
const timestamp = Date.now().toString().slice(-6);
const orderNumber = `PO-${year}${month}${day}-${timestamp}`;
// Includes microsecond precision
```

**Additional Safety**:
- Database unique constraint on `orderNumber`
- Retry logic catches P2002 errors
- Generates new timestamp on retry

---

### 10. Stale Pending Orders

**Problem**: Orders stuck in PENDING state forever

**Prevention**:
- `expectedArrivalDate` calculated at creation
- Scheduled job to detect overdue orders:

```javascript
// Run daily
async function checkOverdueOrders() {
  const overdueOrders = await prisma.purchaseOrder.findMany({
    where: {
      status: { in: ['PENDING', 'IN_TRANSIT'] },
      expectedArrivalDate: { lt: new Date() }
    }
  });

  for (const order of overdueOrders) {
    await createAlert({
      type: 'ORDER_DELAYED',
      severity: 'WARNING',
      message: `Order ${order.orderNumber} is overdue`
    });
  }
}
```

## Caching Strategy

### Cache Keys Pattern

```javascript
CACHE_KEYS = {
  PRODUCT: (id) => `product:${id}`,
  WAREHOUSE: (id) => `warehouse:${id}`,
  WAREHOUSE_CAPACITY: (id) => `warehouse:${id}:capacity`,
  SUPPLIER: (id) => `supplier:${id}`
}
```

### TTL Configuration

```javascript
CACHE_TTL = {
  PRODUCT: 3600,      // 1 hour (stable data)
  WAREHOUSE: 300,     // 5 minutes (changes frequently)
  SUPPLIER: 3600      // 1 hour (stable data)
}
```

### Cache Invalidation Points

- **Product Update**: Clear CACHE_KEYS.PRODUCT(id)
- **Warehouse Update**: Clear WAREHOUSE + WAREHOUSE_CAPACITY
- **Stock Change**: Clear PRODUCT + WAREHOUSE + WAREHOUSE_CAPACITY
- **Order Arrival**: Clear all related caches

## Transaction Management

### Atomic Operations

**Critical Transactions**:
1. Order arrival (stock update + warehouse update + movement record)
2. Stock adjustment (stock + warehouse + audit trail)

**Retry Policy**:
- Deadlock: Retry up to 3 times
- Constraint violation: Retry with new data (order numbers)
